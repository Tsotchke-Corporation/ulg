## Two facts about the solver that this document established

1. **Stiffness is tied to dt** (`:17-26`). `sphPhaseDemo.js` "caps each
   phase's sound speed at `cflSafety × L / dt` and scales the moduli by
   (c_cap / c_real)²". "Liquids are therefore already weakly compressible: an
   artificial sound speed of a few m/s instead of water's 1,480 m/s." "the app
   now softens liquids about 1e5×" (`:213-214`). So every scene's material
   stiffness is a numerical choice set by dt, and "the 'exact small-dt run' is
   itself stiffness-dependent".
2. **MPM's dt sensitivity is not time-integration error** (`:221-231`). "At 0.5
   ms, RK2 and Euler differ by only 0.04% in momentum. Halving dt still moves
   momentum by about 1.95% ... The cause is MPM's per-step transfer filtering.
   Every P2G/G2P round trip smooths sub-grid velocity, so the smoothing per
   simulated second scales with 1/dt. At a fixed grid a smaller dt is not 'more
   converged', only differently smoothed." "**Consequence.** '1% against a
   finer-dt run' is not a well-posed gate for MPM: the reference is no closer
   to the true solution."

The gate was therefore re-posed against physics (`:233-278`): the first
sloshing mode of a tank, scored against `ω² = g k tanh(k h)`. "The implicit
operator meets the 1% budget on the physical observable (the mode frequency)
through **c·dt/dx ≤ 6.4**, on both grids." It diverges at 12.8. "Numerical
damping scales with the number of transfers, so coarser dt is *closer* to
water's real damping". "**Envelope rule.** Accept the operator for c·dt/dx ≤
6.4. Outside that, sub-step exactly."

## The operator (`:75-98`, `:144-186`)

"Linearize the explicit P2G particle-stress force in J_{n+1}: p_{n+1} ≈ p_n −
θ K dt div_p(v_{n+1})", with "K the Eshkol-derived ρ dp/dρ". The grid system
`(I + A)v = b`, `A = (dt²/m) Dᵀ K D`, is solved by matrix-free conjugate
gradients on the GPU. "The operator reduces exactly to explicit at the same
dt". It "binds 10 storage buffers, so it needs
`maxStorageBuffersPerShaderStage` above the default 8".

Where Eshkol enters (`:104-117`, `:420-436`):

- `src/runtime/material/eshkolEosStiffness.js` builds each phase's EOS program
  and defines `(eos-stiffness rho) = rho · (derivative eos-pressure rho)`.
  "Eshkol's forward-mode AD samples it in the warm client VM worker (A6). An
  A4 `fitResponseFunction` (Chebyshev, held-out residuals, strict box ...)
  turns the samples into a GPU-evaluable K(ρ)."
- `scripts/derive-eshkol-eos-stiffness-table.mjs` runs that derivation and
  "writes `src/runtime/material/eshkolEosStiffnessTable.js`. The GPU solve
  evaluates the table by Clenshaw from the params uniform, and the receipt
  reads `stiffnessSource: eshkol-derived-chebyshev-v1`." "The closed form
  remains as the out-of-domain fallback and the A/B arm."
- "A new liquid EOS now needs only its Eshkol definition and a table
  regeneration."

So the chain law program → Eshkol AD → A4 fit → resident GPU evaluator →
receipt exists end to end for one function. The table is generated by a script
and checked in; it is not derived during a run, and nothing invalidates it on
an envelope exit. For Tait the derivative is known in closed form ("Eshkol AD
reproduces this closed form to 2e-16"), so what this proves is the pipeline,
not new physics.

## Where it runs (`:280-304`)

`src/runtime/sph/sphImplicitPressureGpu.js`, "on the Tier-0 fused sequence,
between grid update and G2P". "Solids, gas and invalid volumes contribute
nothing." "The reaction-table product rows are not threaded: reaction scenes
do not run Tier-0." Knobs: `implicitPressure=1`, `implicitCfl`,
`implicitIters`; iteration rule `max(10, ⌈5·c·dt/dx⌉)`.

It is on one route (Tier0), for one phase class (liquids), and on by default in
one preset (water-realtime). Iron Ice, sodium-water, cesium-fluorine and
water-cycle run the canonical lane, which does not have it.

## What made water-realtime real-time (`:313-462`)

| Run (36,864 particles, headless) | steps/s | sim-s per wall-s | display |
|---|---|---|---|
| default explicit 1 ms, 2 substeps per frame | 112 | 0.11 | ~56 fps |
| explicit 1 ms, real-time pacing, 512 steps/schedule | 645 | 0.65 | 60 fps |
| implicit 8 ms, pacing, 256 steps/schedule | 127 | 1.02 | ~19 fps |
| preset default after pipelining, Eshkol K, c·dt/dx 3 | — | **1.29** | 60 fps, k = 3 |

- "**The wall was presentation QoS, not the GPU.** Tier-0 submits 2 substeps
  per presented frame ..., and each boundary is a blocking round trip, so
  flag-off was capped at about 112 steps/s with the GPU 6% busy" (`:382-386`).
- Real-time pacing: "k = ⌈measured frame period / dt⌉ ... a fixed timestep
  with a variable number of steps per frame." Pipelined boundaries: "The
  frame's draw is an extrapolated temporal frame submitted at the boundary's
  start."
- Note the second row: explicit stepping alone reached 0.65 of real time once
  pacing was fixed. The implicit operator supplied the last factor of two.
- Determinism: the scatter moved from f32 compare-and-swap to 64-bit fixed
  point, so "**flag-on steps are now bit-reproducible**". "A timing hack that
  suggested 45× faster integer atomics was an artefact".
- Accuracy at the default (c = 375·dx, 8 ms, 15 iterations) against explicit
  1 ms: positions 3.8%, momentum 1.2%, kinetic energy +5.0%; explicit at half
  dt differs from explicit 1 ms by 2.7%, 0.8%, −4.4% (`:448-453`).
- Open: 106-109 boundary proof failures per 30 s, "pre-existing" and
  fail-open; "The 'unavailable' count is exactly 63 in every run".

## How this fits (Hermes, INFERRED)

- This is the Star Spec's ladder in miniature: a derived closure with a
  validity envelope (`c·dt/dx ≤ 6.4`) and an exact fallback (sub-step). It is
  also the first use of A4 and A6 by a law in the hot loop.
- It attacks the number of steps per simulated second. It does not change the
  cost of a canonical step, which is where Iron Ice's time goes. To help the
  plume scenes it would have to run on the canonical lane and handle solids
  and gas, or those scenes would have to run on a Tier0-like fused route.
- The envelope is a single global number today. In the scale-adaptive design
  it would be evaluated per SS node, with exact sub-stepping only where it
  fails. That needs per-level or per-region time stepping in SS, which does
  not exist (the only time subdivision is the two-level macro's retry).
